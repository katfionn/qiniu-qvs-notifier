## 一、产品概述

### 1.1 产品定位
七牛 QVS 通知器是一个通用的设备状态监控与告警平台，支持多服务商、多账号、多设备的灵活配置，并提供设备级的通知渠道管理能力。

### 1.2 核心价值
- **多服务商支持**：不局限于七牛 QVS，支持接入任何提供 API 的设备监控服务商
- **灵活的通知体系**：支持为每个监控任务配置独立的通知渠道
- **可扩展架构**：通过标准化的服务商配置模式，快速接入新的服务商
- **多用户协作**：支持账号体系，适用于团队使用场景

### 1.3 目标用户
- 运维工程师：需要监控多个平台的设备状态
- 系统管理员：需要为团队配置统一的监控系统
- 开发人员：需要接收设备异常告警

## 三、详细功能需求

### 3.1 任务列表

#### 3.1.1 功能说明
任务是系统的核心概念，表示一个完整的监控配置。每个任务关联：
- 1 个监听渠道（数据来源）
- N 个通知渠道（告警目标）
- N 个设备（监控对象）

#### 3.1.2 列表页面

**页面路径**: `/tasks`

**列表字段**:

| 字段名 | 类型 | 说明 | 交互 |
|--------|------|------|------|
| 任务名称 | String | 用户自定义 | 点击可编辑 |
| 渠道 | String | 展示格式：`渠道名称（服务商）` | - |
| 国标 ID | String | 关联的国标设备 ID | - |
| 设备 | Number | 监听的设备数量 | 点击弹窗展示设备列表 |
| 通知渠道 | Tag[] | 关联的通知渠道名称 | 多个渠道用标签展示 |
| 状态 | Enum | `运行中` / `已停止` | 状态徽章 |
| 创建日期 | DateTime | YYYY-MM-DD HH:mm:ss | - |
| 修改日期 | DateTime | YYYY-MM-DD HH:mm:ss | - |
| 操作 | Actions | - | 见下方 |

**操作按钮**:

| 操作 | 图标 | 条件 | 说明 |
|------|------|------|------|
| 编辑 | 铅笔 | 始终显示 | 进入编辑页面 |
| 日志 | 文档 | 始终显示 | 打开日志抽屉 |
| 开始任务 | 播放 | 状态=已停止 | 启动任务执行 |
| 停止任务 | 暂停 | 状态=运行中 | 停止任务执行 |
| 删除 | 垃圾桶 | 始终显示 | 二次确认后删除 |

**页面顶部操作**:
- 新建任务按钮（主按钮，右上角）
- 搜索框（支持任务名称、渠道名称搜索）
- 筛选器（按状态、服务商筛选）

#### 3.1.3 日志查看

**展示方式**: 右侧抽屉（Drawer）

**日志结构**:
```
| 执行时间 | 执行次数 | 国标设备号 | 设备号 | 状态 | 通知状态 |
|------|------|------|------|----------|------|
| 2026-09-03 14:30:00 | 1 | XXXXXXX | xxxxxxxxxxxxxxxxxx | 离线 | 已通知 |
| 2026-09-03 14:32:00 | 1 | XXXXXXX1 | xxxxxxxxxxxxxxxxxx2 | 在线 | 未通知 |
| 2026-09-02 14:34:00 | 2 | XXXXXXX3 | xxxxxxxxxxxxxxxxxx3 | 离线 | 通知失败 |
```
> 通知失败出现于已经发送通知但是请求后返回报错、并且经过所有重试手段后都依旧报错的情形

> 日志展示按精美的TUI进行呈现，兼容TUI版本的；排序按照执行次数排顺序、同一个执行次数内按执行时间排顺序，默认每次打开的窗口都固定滚动到最下方最新记录的位置

> TUI版本的日志还需要支持输入数字筛选最近N次执行次数的记录、或最近N条记录

**日志字段**:
- 执行时间
- 设备名称/ID
- 设备类型（根据服务商配置动态展示）
- 状态变化
- 通知发送结果
- 错误信息（如有）

**日志筛选**:
- 按日期范围筛选
- 按设备筛选
- 按状态变化筛选（仅显示状态变化的记录）

#### 3.1.4 设备弹窗

**触发**: 点击设备数量

**弹窗内容**:

| 设备名称 | 设备类型 | 设备 ID | 当前状态 | 最后更新时间 |
|----------|----------|---------|----------|--------------|
| 摄像头-001 | Camera | gb_12345 | 在线 | 2026-09-03 14:30 |
| NVR-002 | NVR | gb_67890 | 离线 | 2026-09-03 14:25 |

#### 3.1.5 添加/编辑任务

**页面路径**: `/tasks/new` 或 `/tasks/:id/edit`

**表单字段**:

##### 基础信息

| 字段 | 类型 | 必填 | 说明 | 验证规则 |
|------|------|------|------|----------|
| 任务名称 | Input | 是 | - | 1-50字符 |
| 监听渠道 | Select | 是 | 数据源：监听渠道列表 | - |

##### 服务商配置（动态字段）

根据选择的监听渠道，动态加载该服务商所需的配置字段。

**七牛 QVS 示例**:
- 空间名称（Select，通过 API 获取）
- 国标设备（Select，通过 API 获取）
- 具体设备（Multi-Select，通过 API 获取）

##### 监听配置

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| 监听状态 | Multi-Select | 是 | 根据服务商能力动态加载（如：在线、离线、故障） |

##### 执行周期

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| 执行类型 | Radio | 是 | `一次性` / `周期性` |
| 执行时间 | DateTime | 执行类型=一次性时 | 指定执行时间 |
| Cron 表达式 | Input | 执行类型=周期性时 | 支持标准 Cron |
| Cron 可视化编辑器 | Component | - | 辅助生成 Cron 表达式 |

**Cron 可视化编辑器**:
- 每 N 分钟
- 每 N 小时
- 每天（指定时间）
- 每周（指定星期和时间）
- 每月（指定日期和时间）
- 自定义（直接输入 Cron 表达式）

##### 通知渠道

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| 通知渠道 | Multi-Select | 是 | 数据源：通知渠道列表 |

**空状态处理**:
- 如果没有可选的通知渠道，显示：
  ```
  ⚠️ 暂无可用的通知渠道
  
  [立即配置通知渠道]
  ```
- 点击按钮跳转至 `/notification-channels/new`

**表单提交**:
- 保存：保存任务但不启动
- 保存并启动：保存任务并立即启动
- 取消：返回列表页

**表单验证**:
- 实时验证（输入时）
- 提交前全量验证
- 错误提示在字段下方红色文字显示

### 3.2 监听渠道配置

#### 3.2.1 功能说明
监听渠道定义了从哪个服务商获取设备数据。每个渠道包含：
- 服务商信息
- 认证凭据
- API 配置

#### 3.2.2 列表页面

**页面路径**: `/source-channels`

**列表字段**:

| 字段名 | 类型 | 说明 |
|--------|------|------|
| 渠道 ID | String | 系统生成 |
| 渠道名称 | String | 用户自定义 |
| 服务商 | String | 如：七牛 QVS |
| 认证状态 | Badge | `已认证` / `未认证` / `已过期` |
| 创建日期 | DateTime | - |
| 修改日期 | DateTime | - |
| 操作 | Actions | 编辑/启用/停用/删除 |

**认证状态说明**:
- ✅ 已认证：认证信息有效
- ❌ 未认证：未配置或认证失败
- ⚠️ 已过期：认证信息已过期

**启用/停用**:
- 停用的渠道不能被任务选择
- 已被使用的渠道不能删除（需先删除关联任务）

#### 3.2.3 添加/编辑渠道

**页面路径**: `/source-channels/new` 或 `/source-channels/:id/edit`

**表单字段**:

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| 渠道名称 | Input | 是 | 1-50字符 |
| 服务商 | Select | 是 | 数据源：系统设置 > 渠道配置 |

**服务商认证信息（动态字段）**:

根据选择的服务商，动态加载认证字段。

**七牛 QVS 示例**:
- Access Key（Input，必填）
- Secret Key（Password，必填）

**表单底部**:
- 测试连接按钮：验证认证信息是否有效
- 保存按钮
- 取消按钮

### 3.3 通知渠道配置

#### 3.3.1 功能说明
通知渠道定义了告警消息发送到哪里。支持多种通知方式。

#### 3.3.2 支持的通知方式

##### NTFY.sh
- 服务地址（默认：https://ntfy.sh）
- Topic 名称
- 优先级（可选）
- 标签（可选）

##### Webhook
- URL 地址
- 请求方法（POST/GET/PUT）
- Query 参数（键值对）
- Headers（键值对）
- Request Body（JSON 编辑器）
- 跳过 SSL 验证（Checkbox）

#### 3.3.3 列表页面

**页面路径**: `/notification-channels`

**列表字段**:

| 字段名 | 类型 | 说明 |
|--------|------|------|
| 渠道 ID | String | 系统生成 |
| 渠道名称 | String | 用户自定义 |
| 渠道方式 | Tag | NTFY / Webhook |
| 地址 | String | NTFY Topic 或 Webhook URL |
| 创建时间 | DateTime | - |
| 修改时间 | DateTime | - |
| 操作 | Actions | 编辑/查看/删除 |

#### 3.3.4 添加/编辑通知渠道

**页面路径**: `/notification-channels/new` 或 `/notification-channels/:id/edit`

**表单字段**:

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| 渠道名称 | Input | 是 | 1-50字符 |
| 通知方式 | Radio | 是 | NTFY / Webhook |

##### NTFY.sh 配置

| 字段 | 类型 | 必填 | 默认值 |
|------|------|------|--------|
| 服务地址 | Input | 是 | https://ntfy.sh |
| Topic | Input | 是 | - |
| 优先级 | Select | 否 | default |
| 标签 | Input | 否 | - |

##### Webhook 配置

| 字段 | 类型 | 必填 | 默认值 |
|------|------|------|--------|
| URL | Input | 是 | - |
| 请求方法 | Select | 是 | POST |
| Query 参数 | KeyValue | 否 | - |
| Headers | KeyValue | 否 | - |
| Request Body | JSON Editor | 否 | {} |
| 跳过 SSL 验证 | Checkbox | 否 | false |

**Request Body 变量支持**:
```json
{
  "msgtype": "text",
  "text": {
    "content": "{{task_name}} 检测到设备 {{device_name}} 状态变化：{{old_state}} → {{new_state}}"
  }
}
```

**可用变量**:
- `{{task_name}}`: 任务名称
- `{{device_name}}`: 设备名称
- `{{device_id}}`: 设备 ID
- `{{old_state}}`: 旧状态
- `{{new_state}}`: 新状态
- `{{timestamp}}`: 时间戳

**表单底部**:
- 发送测试通知按钮
- 保存按钮
- 取消按钮

#### 3.4.3 渠道配置

**功能说明**:
配置系统支持的服务商及其 API 规范。

##### 配置方式 1：自动解析

**交互流程**:

1. 用户点击"自动解析配置"
2. 显示提示词模板和输入框：
   ```
   请将以下提示词和服务商文档地址提供给 AI：
   
   【提示词】
   请根据以下服务商文档，提取设备监控相关的 API 配置信息，
   并以 JSON 格式输出...
   
   【文档地址】
   [输入框：请输入服务商文档 URL]
   
   [复制提示词] 按钮
   ```
3. 用户将提示词和文档 URL 复制给 AI
4. AI 返回 JSON
5. 用户将 JSON 粘贴到系统
6. 系统解析并生成配置

**JSON 格式规范**:
```json
{
  "provider_name": "七牛 QVS",
  "provider_code": "qiniu_qvs",
  "auth_type": "ak_sk",
  "auth_fields": [
    {
      "key": "access_key",
      "label": "Access Key",
      "type": "string",
      "required": true
    },
    {
      "key": "secret_key",
      "label": "Secret Key",
      "type": "password",
      "required": true
    }
  ],
  "api_base_url": "https://qvs.qiniuapi.com",
  "capabilities": [
    {
      "name": "list_namespaces",
      "label": "获取空间列表",
      "method": "GET",
      "path": "/v1/namespaces",
      "params": [],
      "response_path": "items"
    },
    {
      "name": "list_devices",
      "label": "获取设备列表",
      "method": "GET",
      "path": "/v1/namespaces/{namespace_id}/devices",
      "params": [
        {
          "key": "namespace_id",
          "source": "path"
        }
      ],
      "response_path": "items"
    }
  ]
}
```

### 3.5 账号体系

#### 3.5.1 用户角色

##### 管理员
- 查看/编辑所有任务
- 管理监听渠道
- 管理通知渠道
- 管理用户
- 配置系统设置

##### 普通用户
- 查看/编辑自己的任务
- 查看监听渠道（不可编辑）
- 查看/编辑自己的通知渠道
- 查看自己的资料

#### 3.5.2 默认管理员

**初始化规则**:
- 系统首次启动时创建默认管理员
- 用户名：admin

## 十、风险和挑战

### 10.1 技术风险

#### 10.1.1 动态服务商配置
**风险**: 不同服务商的 API 差异大，难以抽象统一接口
**缓解措施**: 
- 设计灵活的适配器模式
- 提供完善的 JSON Schema 规范
- 预先适配 2-3 个主流服务商验证可行性

#### 10.1.2 任务调度稳定性
**风险**: 大量任务并发执行可能导致资源耗尽
**缓解措施**:
- 限制最大并发任务数
- 任务队列化处理
- 失败重试机制

### 10.2 产品风险

#### 10.2.1 用户学习成本
**风险**: 动态配置功能过于复杂，用户难以上手
**缓解措施**:
- 提供详细的使用文档
- 内置常见服务商的配置模板
- 提供配置向导

#### 10.2.2 服务商 API 变更
**风险**: 服务商修改 API 导致配置失效
**缓解措施**:
- API 版本管理
- 定期检查认证状态
- 提供快速更新配置的通道

## 十一、FAQ

### 11.1 产品相关

**Q: 为什么不直接支持所有服务商，而是要用户自己配置？**

A: 设备监控服务商众多，每个服务商的 API 设计差异很大。预置所有服务商不现实，且会增加维护成本。通过动态配置，用户可以快速接入任何服务商，同时也为未来的服务商提供了扩展性。

**Q: 普通用户和管理员的区别是什么？**

A: 管理员可以管理所有用户、所有渠道配置，普通用户只能管理自己的任务和通知渠道。这种设计适用于团队协作场景。

**Q: 为什么日志记录要按设备粒度存储？**

A: 按设备粒度存储日志，可以方便用户追踪单个设备的状态变化历史，有助于排查问题。

### 11.2 技术相关

**Q: 为什么选择 SQLite 而不是 MySQL/PostgreSQL？**

A: SQLite 足够满足中小规模部署需求，无需额外的数据库服务，降低部署复杂度。如果未来需要支持大规模部署，可以通过 ORM 切换到 PostgreSQL。

**Q: 任务调度使用什么方案？**

A: 使用 APScheduler，支持 Cron 表达式和一次性任务，足够灵活且成熟。

**Q: 前端为什么使用 Vue 而不是 React？**

A: Vue 3 的 Composition API 提供了良好的代码组织方式，Element Plus 组件库成熟度高，适合快速开发后台管理系统。
